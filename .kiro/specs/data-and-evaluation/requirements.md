# 요구사항: 데이터와 합성 시나리오 평가 (data-and-evaluation)

담당: D. 출처: `docs/PRD.md`, `docs/기능명세서.xlsx` 영역 9(데이터 소스), 10(합성 시나리오 평가). 결과 화면 UI는 `app-ui-kiro` 스펙에서 다룬다.

## 소개

공공데이터 8종 소스를 검증하고, 통과분만 사전 수집한 JSON으로 번들한다. 런타임에는 외부 API를 부르지 않는다. 합성 시나리오로 성공 지표를 측정하고, 모든 수치가 합성 시나리오 기준임을 명시한다.

## 요구사항

### 1. 데이터 소스 검증

**사용자 스토리:** 개발자로서, 어떤 소스가 실제로 쓸 수 있는지 먼저 알아야 기능 범위를 정할 수 있다.

1. 시스템은 소스별로 키 발급, 샘플 호출, 응답 스키마 확인 결과를 `data/SOURCES.md`에 기록해야 한다.
2. 대상 소스는 기상청 단기예보, 서울시 실시간 도시데이터, TOPIS 돌발상황정보, 지하철 실시간 도착정보, 서울 버스 도착정보, 지하철 혼잡도 통계, 에어코리아이다.
3. 파업·집회는 공식 API가 없으므로 사용자 제보로 대체하고 `SOURCES.md`에 그렇게 적는다.
4. 검증을 통과한 소스만 실데이터로 쓰고, 실패한 소스는 합성 데이터로 대체해야 한다.
5. 실데이터 검증 대상 자치구는 3곳으로 한정한다.

### 2. 사전 수집과 번들

1. 시스템은 실데이터를 사전에 수집해 정적 JSON으로 번들해야 한다.
2. 앱은 런타임에 외부 API를 호출하지 않아야 한다.
3. 번들 JSON마다 수집 시각과 소스 이름을 메타데이터로 포함해야 한다.
4. API 키와 인증 정보는 레포에 커밋하지 않고 `.env`에서만 읽어야 한다.

### 3. 합성 데이터와 표기

1. 소스를 합성 데이터로 대체하면 시스템은 해당 항목에 `source: 'synthetic'`을 붙여야 한다.
2. 샘플 데이터 모드를 기본값으로 제공해야 한다.
3. 시스템은 결과 화면과 `README.md`에 소스별로 실데이터 사용 또는 합성 대체 여부를 밝혀야 한다.
4. 지역마다 쓸 수 있는 신호가 다르므로 시스템은 자치구별 사용 가능 신호 목록을 데이터로 제공해야 한다.

### 4. 합성 시나리오 평가

**사용자 스토리:** 심사자로서, 실사용자 없이도 "안 울리는 날의 가치"가 숫자로 확인되길 원한다.

1. 평범한 날 시나리오에서 시스템은 알림을 0건 내야 한다.
2. 이상을 주입한 시나리오에서 시스템은 주입한 이상의 80% 이상을 탐지해야 한다.
3. 시스템은 같은 시나리오를 고정 임계값 방식으로 돌려, 알림 수가 50% 이상 감소했는지 비교해야 한다.
4. 시스템은 참고 지표로 알림 수 대비 '도움됨' 비율을 계산해야 한다.
5. 평가는 `anomaly-engine`의 `runDay`를 그대로 호출해야 하고, 평가용 별도 판정 로직을 두지 않는다.
6. 평가 결과에는 "합성 시나리오 기준"이라는 문구가 항상 포함되어야 한다.

## 미확정 사항 (가정 포함)

| 항목 | 가정 | 확정 필요 |
|---|---|---|
| 검증 자치구 3곳 | 미정 (출근 2호선 경로가 지나는 구 우선) | 팀 선정 |
| 소스 통과 여부 | 전 소스 미검증, 착수 30분 내 확인 | 검증 결과 |
| 고정 임계값 | 편차 z ≥ 1.0이면 알림 (기존 앱 방식의 대용) | 팀 합의 |
| 합성 시나리오 규모 | 페르소나 2종 × 평범한 날 7일 + 이상 주입 일 10건 | 튜닝 결과 |

## 추가 요구사항: 공공 파일 기준선

1. 제공된 원본 CSV/XLSX를 변경하지 않고 파일명·SHA256·기간·행수·결측·중복을 기록해야 한다.
2. 최신 분기 혼잡도를 기본으로 쓰되 호선·방향·요일·시간을 식별해야 한다.
3. 승하차 인원, 열차 혼잡도, 지역 인구, 대기질은 단위와 의미를 구분해야 한다.
4. 현재 관측이 없으면 과거 파일이나 합성 신호로 실제값을 대체했다고 숨기지 않아야 한다.
