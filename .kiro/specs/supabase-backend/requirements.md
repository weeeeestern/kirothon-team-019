# 요구사항: Supabase 백엔드 (supabase-backend)

담당: `backend-dev`(스키마, RPC, 수집), `ui-dev`(앱 연결), `qa`(검증). 경계는 `.kiro/steering/api-contract.md`를 따른다.

## 소개

`citizen-report-points` 스펙은 "같은 경로의 서로 다른 사용자 2명 확인"을 요구하지만, 브라우저 `localStorage`만으로는 다른 사용자의 제보와 확인을 볼 수 없다. 여러 사용자가 공유해야 하는 데이터(제보, 확인, 도움됨, 포인트)만 Supabase로 옮긴다. 판정과 개인 경로는 브라우저에 남긴다.

## 요구사항

### 1. 익명 사용자

**사용자 스토리:** 사용자로서, 가입 없이 제보하고 확인하고 싶다.

1. 앱이 Supabase에 연결되면 시스템은 익명 로그인으로 사용자 ID를 만들어야 한다.
2. 시스템은 이메일, 전화번호, 위치, 경로의 정류장 목록과 출발 시각을 서버에 저장하지 않아야 한다.

### 2. 제보 저장

1. 사용자가 제보하면 시스템은 `submit_report` RPC로 제보를 저장하고 작성자에게 +10 포인트를 한 번만 적립해야 한다.
2. 유형이 6종(`construction`, `strike`, `marathon`, `congestion`, `rain`, `dust`)이 아니거나, 장소가 비었거나 60자를 넘거나, 설명이 100자를 넘으면 시스템은 저장하지 않고 오류를 돌려줘야 한다.
3. 제보에는 경로를 가리키는 값으로 경로 키(`route_key`, 예: 노선과 구간 이름)만 저장한다. 사용자의 정류장 목록과 출발 시각은 저장하지 않는다.
4. 클라이언트는 `reports` 테이블에 직접 insert/update/delete 할 수 없어야 한다.

### 3. 제보 확인 (2인 규칙)

1. 사용자가 다른 사람의 제보를 확인하면 시스템은 `confirm_report` RPC로 확인을 기록해야 한다.
2. 작성자 본인의 확인, 같은 사용자의 중복 확인, 다른 경로 키의 확인, 제보한 날(서울 시간)이 지난 확인은 기록하지 않아야 한다.
3. 작성자가 아닌 서로 다른 사용자 2명이 확인하면 제보는 '확인됨'이 되어야 한다.
4. 사용자는 같은 경로 키의 오늘 제보와 확인 수, 확인됨 여부를 읽을 수 있어야 한다. 다른 사용자의 ID는 읽을 수 없어야 한다.

### 4. 도움됨과 포인트

1. 사용자가 확인된 제보에 '도움됨'을 누르면 시스템은 `mark_helpful` RPC로 기록하고 작성자에게 +5 포인트를 한 번만 적립해야 한다.
2. 작성자 본인, 같은 사용자의 중복, 확인되지 않은 제보에는 적립하지 않아야 한다.
3. 사용자는 자기 포인트 원장만 읽을 수 있어야 하고, 원장에 직접 쓸 수 없어야 한다.
4. 알림 피드백 +1 포인트는 `record_feedback` RPC로 알림 ID당 한 번만 적립해야 한다.

### 5. 데모 모드 유지

1. `VITE_SUPABASE_URL` 또는 `VITE_SUPABASE_ANON_KEY`가 없으면 앱은 지금의 `localStorage` 데모로 동작해야 한다.
2. Supabase 호출이 실패해도 앱은 멈추지 않고 화면에 "연결이 불안정해요" 안내를 보여 줘야 한다.

### 6. 공공데이터 수집 (선택)

1. Edge Function `collect-citydata`는 서울 실시간 도시데이터의 사고·통제, 혼잡, 날씨를 받아 `snapshots`에 저장해야 한다.
2. API 키는 Supabase 시크릿에서만 읽고, 응답과 로그에 키나 요청 URL을 남기지 않아야 한다.
3. 앱은 런타임에 공공데이터 API를 직접 호출하지 않는다. 이 기능은 판정에 바로 쓰지 않고 데이터 근거로 둔다.

## 범위 밖

- 판정 엔진의 서버 이전, 푸시 알림, 원격 배포 자동화(`db push`, `functions deploy`는 사람이 승인).
- 제보 위치 지도 표시, AI 제보 검증.

| 수집 주기 | 10분 | 비용 확인 |
