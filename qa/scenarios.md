# 데모 시나리오

각 항목은 "조작 → 기대 결과 → 확인 방법"이에요. 확인 방법의 "수동"은 사람이 직접 해 봐야 한다는 뜻이에요.

## S-R1. 익명 사용자 2명으로 제보 → 확인 2회 → 알림 → 도움됨 +5 (supabase-backend 3.3, 4.1, 5.1)

준비: `npx supabase start`, `src/.env.local`에 `VITE_SUPABASE_URL`(로컬 API 주소)과 `VITE_SUPABASE_ANON_KEY`(`npx supabase status`의 anon 키)를 넣고 `npm run dev`. 키 값은 커밋하지 않아요.
브라우저 3개가 필요해요: 제보자 A, 확인자 B, 확인자 C. 같은 브라우저의 다른 탭은 세션을 공유하므로 서로 다른 브라우저나 시크릿 창을 써요. 세 곳 모두 같은 구와 같은 출발·도착 역의 경로를 등록해요(경로 키가 같아야 해요).

| 단계 | 조작 | 기대 결과 | 확인 방법 |
|---|---|---|---|
| 1 | A: 제보 탭에서 상황, 경로의 역, 시각을 입력하고 제보 | "+10 P" 토스트, 키로 `proud`, A의 포인트 10 | 수동. DB는 `public.point_ledger`에 `report:<id>` 1행 (`supabase/tests/reports_points.test.sql`) |
| 2 | A: 같은 제보를 다시 제출하지 않고 새로고침 | 포인트는 10 그대로 | 수동 |
| 3 | B: 제보 탭을 열기 | A의 제보가 "검증 대기", 확인 0/2로 보임. 다른 사용자 ID는 화면과 네트워크 응답에 없음 | 수동. 뷰 `report_status`에 사용자 열이 없음 |
| 4 | B: "같은 경로예요 · 확인" | "확인을 남겼어요", 확인 1/2, 아직 "검증 대기" | 수동. pgTAP "1명 확인: 확인 수 1" |
| 5 | B: 같은 버튼을 다시 | "이미 확인했어요", 확인 수는 1 그대로 | 수동. pgTAP "같은 사용자의 중복 확인은 거부해요" |
| 6 | A: 자기 제보 확인 시도 | 버튼이 없음(작성자). RPC로 직접 호출해도 `self_confirm` | pgTAP "작성자 본인 확인은 거부해요", 트리거 |
| 7 | C: "같은 경로예요 · 확인" | 확인 2/2, "확인됨" | 수동. pgTAP "서로 다른 사용자 2명 확인 시 confirmed" |
| 8 | A, B, C: 홈과 알림 탭 | 확인된 제보가 등록 경로·시각에 영향이 있으면 알림이 1건 생기고 권고 한 줄이 있음. 영향도가 T 미만이면 알림이 없고 이유는 영향도 조건 문구로 보임 | 수동. 알림 생성은 `anomaly-engine`이 판정 |
| 9 | B: "도움이 됐어요" | "제보자에게 도움됨을 전했어요" | 수동 |
| 10 | A: 포인트 확인(최대 30초 안에 자동 갱신) | 포인트 15 (제보 10 + 도움됨 5) | 수동. pgTAP "도움됨 +5" |
| 11 | B: "도움이 됐어요"를 다시 | "이미 도움됨을 눌렀어요", A의 포인트는 15 그대로 | pgTAP "같은 사용자의 도움됨 중복은 false" |
| 12 | C: "도움이 됐어요" | A의 포인트 20 (다른 사용자의 도움됨은 따로 인정) | pgTAP "작성자 합계" |
| 13 | A: 알림 상세에서 "도움이 됐어요" 피드백 | "+1 P" 토스트, A의 포인트 +1, 같은 알림에는 한 번만 | pgTAP "피드백 +1이 알림 ID당 한 번씩" |
