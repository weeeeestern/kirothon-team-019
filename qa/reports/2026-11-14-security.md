## 항목별 결과

### 1. 비밀 정보
- 추적 파일 중 `.env`, `*.key`, `*.pem`은 없다. 추적되는 것은 `src/.env.example` 하나이고 값은 모두 비어 있다(변수 이름 10개, 값 길이 0).
- `supabase/.temp/`와 `supabase/.branches/`는 `supabase/.gitignore`가 무시한다(`git check-ignore`로 확인). 로컬 파일 `supabase/.temp/start-secrets/.../docker.env`도 무시된다. `git ls-files supabase`에는 추적 파일이 아직 없다. 커밋할 때 `git add supabase/`로 추가하면 `.temp`와 `.branches`는 제외된다. 단, `git add -f`는 쓰지 않는다.
- `service_role`, JWT(`eyJ...`), `sb_secret`, 개인 키 블록은 레포 전체에서 문서와 훅 정규식 설명 외에 발견되지 않았다. 코드와 JSON에는 없다.
- 브라우저 코드가 읽는 환경변수는 `src/api/index.ts`의 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` 두 개뿐이다.
- `src/.env.example`에 `VITE_SUPABASE_*`가 없고 옛 이름 `NEXT_PUBLIC_SUPABASE_*`만 있는 것은 보안 위험이 아니다. 값이 비어 있고 앱은 변수가 없으면 로컬 모드로 동작한다. 다만 `NEXT_PUBLIC_KAKAO_REST_API_KEY`가 예시에 남아 있으니, 사용자가 수동 조치할 때 `VITE_`가 붙은 이름으로 비밀 키를 바꾸지 않도록 주의한다(예시 파일 주석이 이미 경고한다).

### 2. Supabase RLS와 RPC
- 테이블 5개(`reports`, `report_confirmations`, `report_helpful`, `point_ledger`, `snapshots`) 모두 `enable row level security`이다.
- 5개 테이블과 `snapshots_id_seq`의 권한을 `public, anon, authenticated`에서 모두 거두었다. 클라이언트에는 `point_ledger`의 `select`(자기 행만, `user_id = auth.uid()`)만 있고 insert/update/delete 정책과 권한은 없다. 직접 쓰기는 거부된다.
- 4개 RPC는 모두 `security definer`와 `set search_path = public`을 가지고, `anon`과 `public` execute를 거두고 `authenticated`에만 준다. 함수 안에서 `auth.uid()` null 검사와 입력 재검증을 한다(유형 화이트리스트, 장소 1~60자, 설명 ≤100자, 시각 정규식, 경로 키 ≤80자, 알림 ID ≤100자).
- 자기 확인은 RPC(`self_confirm`)와 트리거 `report_confirmations_no_self`, 이중으로 막는다. 확인 수는 작성자를 제외하고 센다. 중복은 기본 키로 막는다.
- 포인트 중복 적립은 `(user_id, id)` 기본 키와 `on conflict do nothing`으로 막는다. `amount in (1,5,10)` 제약이 있다.
- 다른 사용자의 원장과 ID를 읽을 경로는 없다. 뷰는 `author`, `user_id`를 노출하지 않는다.
- `mark_helpful`의 경로 일치 미검증과 `submit_report` 횟수 제한 부재는 위 표의 medium 두 건으로 평가했다. 둘 다 금전·개인정보 피해가 없고 제보 신뢰도와 포인트의 조작 문제라 BLOCK 기준(high)은 아니다.
- `supabase/config.toml`의 `enable_anonymous_sign_ins = true`는 설계 요구(익명 로그인)에 맞다. 로컬 설정이고 원격 프로젝트의 CAPTCHA와 속도 제한은 대시보드에서 별도로 확인해야 한다.

### 3. XSS
- `dangerouslySetInnerHTML`은 `src/components/KiroAvatar.tsx:15` 한 곳이다. 입력은 `situation`, `outfit`, `expression`을 `Object.hasOwn`으로 화이트리스트 검사한 값과 숫자 `size`, 내부 리터럴 `motion`뿐이다. 제보 장소와 설명은 이 경로로 들어가지 않는다.
- 제보 `place`, `note`는 `Report.tsx`에서 JSX 텍스트로만 렌더된다. `innerHTML`, `eval`, `document.write` 사용은 테스트 파일 외에 없다.

### 4. 입력 검증
- 클라이언트: `Report.tsx`의 `textarea maxLength={100}`, `validReportInput`, 정류장 일치 검사. 서버: RPC와 테이블 check 제약이 같은 제한(유형 6종, 장소 60자, 설명 100자)을 다시 건다. 양쪽에 있다.

### 5. 개인정보
- 위치 권한 요청(`geolocation`, `navigator.` 사용)은 없다. 이메일, 전화번호 수집 코드도 없다.
- 서버로 가는 것은 `routeKey`(자치구, 출발, 도착), 유형, 장소, 시각, 설명이다. 정류장 전체 목록과 출발 시각은 보내지 않는다(`src/features/routes/route.ts`의 `routeKey`). 출발·도착 정류장 이름이 경로 키에 들어가는 것은 스펙의 가정(`<노선>:<출발역>-<도착역>`)과 같다.
- 제보 응답에 사용자 ID는 없고 `isMine` 불리언만 있다.

### 6. 의존성
- `npm --prefix src audit --omit=dev`: low 2건(`deepmerge`, `antd-mobile` 경유). high/critical 없음. 새로 추가된 `@supabase/supabase-js`에서는 취약점이 보고되지 않았다.

### 7. Edge Function
- `supabase/functions/`가 없다(작업 7은 보류). 검사 대상 없음.
